# 第 4 章 CRUD 的一年：我很熟练，也很慌

流水线工人有个特点，我在自己身上看见了：手比脑子快。

一个需求过来，不用想，手已经开始动了。建表、写接口、拼页面、联调、改字段、再加个状态。键盘敲得很响，屏幕滚得很快，一天下来人是空的。你问我这天干了啥，我说“做了三个需求”，再问具体做了啥，我得翻提交记录。

2004 年到 2006 年，我在逊志，写 Java，做中文问答平台的核心开发，也做 Linux 上的部署。那两年我最大的收获不是技术，是熟练。熟练到什么程度？业务方说一半，我就知道他要什么字段；接口文档不用看，我知道返回结构长什么样。

逊志的办事点在宜家家居那栋楼。公司体系是成熟的：运营、架构、测试各有分工，同事也都很出色。我在那儿开始深入用 Java 做 Web 开发。手上有一个独立项目：开发一个类似 MSN 的聊天机器人。此外也做过增值服务。

**熟练不等于成长。流水线能把你练熟，也能把你用废。**

这话不是骂流水线，是骂我自己。熟练本身没错，错在熟练之后那种“我已经会了”的舒服感。舒服感一上来，人就不问了。不问为什么这么分层，不问为什么这个字段要有默认值，不问为什么这段代码三个月前被别人改过一回。

后来我确实慌过一次。没有具体的事故，也没有谁骂我——就是某个再普通不过的时刻，我突然发现自己说不清“为什么这么写”——我只知道“以前就是这么写的”。那一刻有点像开车开到家门口，突然想不起来刚才那十分钟是怎么开过来的。

我没有立刻辞职去读源码，也没有立刻开始写框架。我只是做了件很小的事：每周挑一处“我只会照着写”的地方，去查一遍它为什么这么写。

查着查着就发现，很多“规定”是有原因的，只是原因没写在文档里；也有很多“规定”根本没原因，就是前人顺手写的。这两类东西混在一起，长得一模一样。

这时候最危险的一句话是“一直就是这么写的”。它不是理由，它只是把问题往后传。你今天不问，明天接手的人也不敢问，最后这一整块东西就变成了没人敢碰的祖传代码——它不一定坏，但也没人知道它为什么好。

所以我后来给自己定了个很低的门槛：**每接手一块陌生代码，至少弄明白一个“为什么”。** 一个就够，不求全懂。弄明白一个，你就有了一个可以撬动整块代码的支点；一个都没有，你就只能照着抄。

熟练期还有三种假象，我全中过：
- **快，就是强。** 手快只说明你路径熟，不说明你路径对。
- **不报错，就是稳。** 不报错可能只是没人走到那条分支。
- **别人不问，就是懂。** 别人不问，多半是懒得问，或者已经不指望你了。

这三种假象的共同点是：它们都很舒服。舒服的东西，通常不让你长本事，只让你长年纪。

更麻烦的是，它们还会给你正向反馈。你手快，组长夸你效率高；你不报错，测试说这块挺稳；别人不问，你就默认自己讲清楚了。反馈是真的，结论是假的——你拿到的夸奖，是流水线的夸奖，不是你的。

那怎么把熟练换成成长？我的办法很笨：**每做完一个需求，逼自己回答一次“这次我多会了什么”。** 如果答案是“更熟了”，那这次就没有成长，只有消耗；如果答案是“我知道了原来这个字段不能这么用”，那才算攒下一点东西。

这个答案不用写得多漂亮，一句话就行。攒够十句，它们连起来就是你自己的一本小册子。不是别人教的，是你自己撞出来的。

也有人说，那我换个环境、换个技术栈，是不是就不慌了。我的经验是：**换个环境能换掉腻，换不掉慌。** 慌的根不在你写什么语言，在你不知道自己写的东西为什么值得存在。这个问题的答案，换几家公司都长不出来，只能自己想。

不过我得承认，那两年的熟练也不是白来的。它给了我一样很实用的东西：**模式识别。** 看到一个需求，我能立刻想出它会长成哪几张表、会踩哪几个坑。这东西不高级，但它是地基——没有它，后面那些“设计”“抽象”全是空中楼阁。地基不丢人，丢人的是拿地基当房子。

地基和房子的区别，说穿了就一句：地基是“我知道这里会出问题”，房子是“我知道为什么这里会出问题”。前者靠次数堆，后者靠脑子想。

**本章的一句话**：熟练是手快，成长是嘴能说清——能说清“为什么”，才算真的会。

**今天能用的三条**：
1. 每周挑一处“照着写”的地方，查文档或问人，弄清它为什么存在。
2. 把一个重复了三次的动作，抽成一个小脚本或小工具——哪怕只省你十分钟。
3. 在备忘录里写一句“这周我搞懂的一个为什么”，不写感受，只写原因。

那阵子我以为，只要再熟练一点，慌就会消失。后来发现，慌不会消失，它只是换了个问题：从“我会不会写”，变成“我写的这些东西，凭什么值得存在”。

慌归慌，我不知道从哪下手。直到框架先对我动了手。
