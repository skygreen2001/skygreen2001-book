## 一

先说个误会。

有人听说我写代码用双语，第一反应是：“英语不太好的人，才这么干吧。”

我理解。这就像看见一个人吃饭配两个碗，先猜他胃不好。真实情况是：我这个年纪的程序员，英语学得不算差，也不算好，读文档靠猜、写注释靠蒙，属于那种“能看懂，但不敢保证自己看懂了”的水平。所以我最早的双语习惯，确实有点怂——中文写一遍，怕自己以后看不懂；英文再写一遍，怕别人看不懂。两个都写，图个安心。

但后来我发现，这事跟英语水平关系不大。真正的问题不在“用哪种语言写”，而在**写下来的东西到底是给谁看的**。

## 二

我先说一句可能不太受欢迎的话：

**大部分项目里，注释不是写给人看的，是写给“三个月后的自己”看的，而那个自己，通常也看不懂。**

不是字不认识，是不知道当时为什么这么写。你写过这种注释吗——“// 这里做特殊处理”。特殊在哪儿？处理什么？为什么不能正常处理？三个月后你自己都答不上来。

这就是我想说的那句：

**让英文去编译，让中文去解释。**
**Let English compile. Let Chinese explain.**

这句话不是语言偏好，是分工。英文那部分，是机器要读的东西：标识符、目录结构、接口名、提交信息、给 AI 的提示词。机器读它，编译它，检索它，不需要情感。中文那部分，是人要读的东西：为什么这么写、当时在怕什么、哪条业务规则不能碰。人读它，是为了接手，不是为了背诵。

一句话：**给机器好编译的，给人好理解的。** 别让机器去猜中文语义，也别让人去猜英文缩写。

这句话不是哪天忽然想出来的。它是被一堆麻烦一点点逼出来的——所以第三节不先讲道理，先讲那些麻烦。不讲清楚它们，这句话就只是一句听着挺顺的口号。

到这里，如果你觉得“这不就是注释规范吗”，那我说得还不够。因为它不是一个写作习惯，是我这套框架里最硬的一层东西。

## 三

我这套框架的代码生成，不是设计出来的，是**改规则改出来的**。

一开始只是嫌重复：同样的增删改查、同样的列表页、同样的表单校验，一个项目抄一遍，抄到第三遍就烦了。于是写个小工具，把能自动的部分自动掉——那时候的“规则”，其实是“我这几天懒得写哪几段”。它不严谨，但有效。

后来前端从 Ext JS 那套换成 bootstrap 那一层，麻烦立刻显形：生成器里写死的东西太多，前端一换，生成出来的代码全得回头改。**规则没写清楚的地方，就是换技术栈时要还债的地方。** 那段时间我不是在写新功能，是在一条一条把“我当时顺手那么写”翻译成“以后必须这么写”。

再往后，AI 进来了。AI 有一个好处，也有一个坏处。好处是它不怕重复，你给它规则，它能一直照做；坏处是它只认**写得清楚的规则**——你含糊，它就自由发挥，发挥得还挺自信。

于是这套框架的核心规则，是在跟 AI 来回折腾的过程中一条一条定下来的。不是我先想好一套完美规范再落到代码里，而是反过来：**先有代码，再有反复的修改，最后才有规则。** 说准确点是：这套东西推导了十几年，直到 AI 到来之后，**核心规则的定义才算完成**——不是因为我终于想清楚了，是因为机器把“说不清楚的地方”全部暴露出来了。

所以我现在敢说一句更准确的话：

**框架的核心不是代码，是一套被反复修正的规则。代码只是规则的执行结果。**

这条规则能被翻出来，不是因为我记性好，是因为它落在三个地方：README、框架代码、生成工具。三个层级都带着它，它才算真的定住。

那这条规则是什么时候写下来的？答案有点丢人：很晚。

我把仓库从头翻了一遍。这句条文第一次出现在 README，是 2026 年 7 月的一次文档提交，整段是新增的，不是从哪段旧话里改出来的。也就是说，在它被写下来之前，没有“上一版条文”——只有一堆早就这么写的代码。

代码早到什么时候？2016 年主仓第一次提交里，控制器就已经是英文类名、英文方法名，注释是中文；生成器那时候也已经带着“表和列必须有注释”的校验。再往前那套 Ext JS 的老代码，逐条历史已经查不到了，能看到的只有一份快照——也是同一个样子。

所以顺序是反的：我先这么写了很多年，才想起来把它写成一句话。不是条文规定了实践，是实践攒到一定程度，条文才被补上。

（可复核：`a2c10c11` 2026-07-27 README 首次写入；`0c9b1a0` 2016-11-16 主仓首提代码仍是这个形态；`8efb7dc5` 2017-07-10 生成器已把中文注释拼进英文骨架。）

代码会过时，框架会换壳，语言会换——Rust 也好 React 也好，都只是当时的工具。但“这条规则为什么存在、它挡住的是哪类错误”，这个东西能留下来。而它留下来的前提是：**它被写下来了，而且写得别人能读懂。**

这就接上了前面几章。第 18 章说，能不能交出去，取决于知识能不能被别人读懂。第 19 章说，要用使用者的眼睛看自己写的东西。这一章补最后一块：**能被写下来的规则，才是能被别人接手的东西。** 你脑子里的经验，再值钱，也是你一个人的；写成规则，才是团队的。

## 四

但这句话有边界，不说清楚就是口号。

**第一，双语是要付维护费的。** 中英两份，一定会不一致。代码改了注释没改，英文名改了中文说明没改——这种时候必须有一条裁决顺序，否则两份都不可信。我的做法是：**以代码为准，注释过期就删掉重写，不留“大概是这个意思”的残留**。宁可没有注释，不要有一句骗人的注释。

**第二，团队的语言习惯不是一致的。** 有人英文读得慢，有人中文写得别扭。硬推一套规范，最先反弹的往往是干活最多的人。所以规则要少，要能一句话说清，要允许“这条我做不到，但我保证标识符是英文”这种降级。

**第三，面向国际读者的开源项目，中文注释是障碍。** 这个我认。所以对外开源的部分，注释尽量英文，中文只留在内部文档和提交说明里——不是不写中文，是不把中文塞进别人读不到上下文的地方。

这条规则不是嘴上说说。它在这套框架里落地了三处——README 里是明文，框架代码里是习惯，代码生成工具里是模板。

README 里是明文：**"Code in English, Comment in Chinese."（注释用中文，代码用英语。）** 这条约定到今天还在更新（README 最近一次改动是 2026 年 10 月 22 日），说明它不是一个当年的口号，而是一份一直有人维护的东西。

代码里没有条文，只有习惯。控制器 `Action_Auth` 是英文名，方法叫 `logout()`、`login()` 也是英文，注释却是 `/** 退出 */`、`/** 登录 */`。一个文件这么写不稀奇，几百个文件都这么写，它就不再是“规范”，而是默认动作。

生成工具里最硬。它从数据库的表注释、列注释里取出中文，直接拼进生成的英文代码骨架：`/** 显示{中文注释} */` 配 `public static String xxxShow(...)`。另外还有一道校验：表和列没有注释，生成时直接报错（`nocomment`、`column_nocomment`）。管得是有点宽，但它至少保证了一件事——英文那半边，永远有一句中文兜着。

顺便说个实话：生成器里并没有把这条规则写成一句条文。我把它的文件翻了一遍，没找到这句原文。它是靠默认模板和中英搭配落地的，真正的明文只在 README 里。这也挺像我们这行的作风：规则写得最清楚的地方，往往不是代码。

（说明：以上路径与提交均来自本机仓库只读核对，仓库未做任何改动。）

**第四，也是最要紧的一条：这不是永久真理。** AI 对中文的理解一直在变好。今天要求“英文给机器、中文给人”，是因为机器读中文还不稳、读英文更稳。等它哪天读中文和读英文一样稳了，这条规则的形态一定会变。**规则是有保质期的，写规则的人得知道自己在什么阶段。**

## 五

所以真正能带走的东西，不是“双语”，是一条能直接贴在项目里的条文。

这条规则是我自己的做法，写下来就一句：

```
Code in English, Comment in Chinese.
```

先把这两层关系说清楚，免得看起来像两个不同的主张：前面那句是**领会**——为什么这么分；这一句是**条文**——怎么落到每一次提交里。同一件事的两层，不是两句话。领会管方向，条文管执行。

条文很硬，一句话，不留解释空间：代码用英文，注释用中文。但条文之外，还有三处实现细节，那是我给的建议，不是条文的一部分：

1. **标识符、接口名、提交信息，用英文。** 一句话理由：这些东西要被机器检索、被别人搜索、被 AI 索引，英文的命中率更高。
2. **注释只写“为什么”，用中文。** “做了什么”让代码自己说；注释里只留业务约束、坑、以及“改了会出什么事”。写不出“为什么”，就别写注释。
3. **给 AI 的提示词，写清输入、输出、约束三件事。** 别描述愿景，描述边界：给它什么、要它吐什么格式、哪些绝对不能动。

（这三条是围绕条文展开的实现建议，不是条文本身——条文只有一句。你还要往下延伸——文档、设计说明、提交规范各自用哪种语言——判断标准只有一条：**下一个接手的人能不能读懂。** 具体分到哪种语言，按你团队的实际来，不必照抄。）

这些都很小，小到不像“方法论”。但它们恰好是那种今天下午就能改、改完下个月还在生效的东西。

## 六

最后说个实话。

我年轻时以为，一个程序员的水平体现在他写了多少代码。后来觉得，体现在他造出了什么东西。再后来，被自己造的东西拖垮过一次，才明白：**你留下的不是代码，是别人能不能在你不在场的时候，继续把这件事做对。**

代码会烂，框架会换，语言会过时。规则如果写清楚了，它能活得比这些都久一点。

让英文去编译，让中文去解释。
Let English compile. Let Chinese explain.
